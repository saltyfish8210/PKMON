====================================================================
一、系统目的与应用范围
====================================================================
PKMon 是一个校园 LBS 收集游戏：玩家在校园地图上移动并触发精灵（本项目为“攻城狮”），
答对校园知识题后把精灵收入图鉴。第二阶段确定两项核心功能：自习任务与精灵遭遇、
答题捕获与精灵收录。本文负责第二项功能在客户端一侧的业务分析与网络适配分析。

本文回答四个问题：
  1) 玩家在客户端看到什么、能做什么，一次答题从进入到结束经过哪些界面状态；
  2) 提交结果不确定（超时、断连、页面被杀）时，客户端如何既不重复发奖、也不把成功误报为失败；
  3) 答错之后如何重试，重试与新作答在请求标识上有什么区别；
  4) 现有旧 Demo 客户端与第二阶段接口契约有哪些差异，差异收敛在哪一层。

本模块的职责边界：
  做什么：答题界面的状态与交互、提交与重试策略、结果确认与展示、收藏概览刷新、
    统一网络层（ApiClient / CaptureApi / CollectionApi / DTO / 统一错误）、旧字段与旧路由的适配。
  不做什么：判题、结算、持久化与并发唯一（孙虹毅，服务端）；地图、定位与演示轨迹（赵冠钧）；
    账号注册登录与入口导航（闫昕、余星晨）；图鉴详情、背包列表与资料编辑（后续迭代）。
  明确不承诺：客户端任何位置都不判定“是否捕获成功”；正确答案不下发到客户端，客户端也无从校验。

====================================================================
二、参与者与系统边界
====================================================================
玩家：本模块唯一主动参与者。玩家的目标是完成一次答题、看到可信的捕获结果、
  并在收藏概览中看到与服务器一致的数量。

捕获服务（后端，辅助参与者）：提供题目与结算结果。它决定“这次到底捕获没有”，
  客户端只转述，不参与判定。接口现状见孙虹毅 design/interfaces.json：
  五个接口已实现，但存储为内存替身、身份为 X-Dev-User 开发替身。

会话存储 SessionStore（辅助参与者）：向网络层提供当前 token，并在账号切换或收到
  40101 时清除。网络层只依赖接口，不反向依赖账号页面。

网络环境（约束条件，不是参与者）：移动网络可能超时、断连、重复投递。
  “提交没有拿到响应”是常态而非异常，本模块的分析必须把它当作一等场景。

系统边界：Flutter 客户端内的三部分——答题界面、收藏概览、统一网络适配层。
  服务端的挑战状态机、幂等判定、唯一约束不在本边界内，本文只引用其结论（BR-01～BR-10）。

三、用况分析
====================================================================
3.1 用况清单
  UC-R1 进入答题并取得题目：从地图上的遭遇进入答题页，拿到属于自己的题目。
  UC-R2 提交作答并查看结果：选择一个选项提交，看到服务端结算结果。
  UC-R3 答错后重试：在挑战仍有效时重新作答。
  UC-R4 恢复结果待确认：提交结果不确定时，查明这次到底有没有成功。
  UC-R5 查看收藏概览：查看已收录种类数、总种类数与捕获次数。
  与孙虹毅业务用况的对应：UC-R1←UC-C2，UC-R2←UC-C3，UC-R3←UC-C3（重试分支），
  UC-R4←UC-C4，UC-R5←UC-C5；UC-C1（开发遭遇）由地图/演示入口发起，不在本页面内。

3.2 UC-R1 进入答题并取得题目
  参与者：玩家（主）、捕获服务（辅）
  目标：拿到一道可作答的题目并看到明确的有效期。
  触发：玩家点击地图上的攻城狮（开发期为“模拟遇见攻城狮”入口）。
  前置条件：玩家已登录并持有有效 token；存在属于本人的可用遭遇（spawnId）。
  后置条件：答题页显示题干、选项与有效期；客户端保存 challengeId；不产生任何收录。
  主流程：
    1) 页面进入加载态，调用 CaptureApi.challenge(spawnId)；
    2) ApiClient 携带 token 发出 POST /api/v1/capture/challenge；
    3) 服务端返回挑战（含状态 OPEN 语义的题目与 expiresAt）；
    4) 适配层把响应映射为 ChallengeView；
    5) 页面显示题干与 2～4 个选项，并依据 sourceType 标注“模拟遇见攻城狮”。
  异常流程：
    E1 网络失败或超时：停在加载失败态，给出原因与“重试”，不进入作答；
    E2 40401（遭遇不存在或不属于本人）：按“不存在”提示并返回地图，不使用“无权访问”措辞；
    E3 41001（遭遇已过期）：提示重新遭遇，不显示答题界面；
    E4 40903（该遭遇已收录）：提示已收录并返回，不重复答题；
    E5 50302（题库暂不可用）：提示稍后重试，不把空页面当成正常状态。

3.3 UC-R2 提交作答并查看结果
  参与者：玩家（主）、捕获服务（辅）
  目标：完成一次作答，并得到可信的“捕获/未捕获”结论。
  触发：玩家点击某个选项。
  前置条件：题目已加载；选项来自服务端下发的集合；本次作答已生成新的 requestId。
  后置条件（答对且此前未收录）：显示成功态，收藏概览刷新为服务端的真实数量。
  后置条件（答错）：显示答错态，挑战保持 OPEN，玩家可再次作答。
  主流程：
    1) 页面进入提交中态，禁用选项与返回；
    2) 生成新的 requestId（一次业务提交一个）；
    3) 调用 CaptureApi.answer(requestId, challengeId, optionId)；
    4) 服务端返回 result 与 captureRecordId；
    5) result=CORRECT 且 captureRecordId 非空：显示成功并按 UC-R5 刷新概览；
    6) result=WRONG：显示答错，允许按 UC-R3 重试。
  异常流程：
    E1 超时/断连：转到 UC-R4，不得直接判失败，更不得本地加一；
    E2 40001（含选项不属于该题）：提示参数错误并允许重新选择，挑战未被消耗；
    E3 40902（同 requestId 不同内容）：属客户端缺陷，提示重新作答并生成新标识；
    E4 41001（过期且该请求未处理过）：提示重新遭遇；
    E5 40401（他人或不存在）：按不存在处理，不泄露归属。

3.4 UC-R3 答错后重试
  参与者：玩家（主）
  目标：在挑战仍然有效时再答一次。
  前置条件：上一次结果为 WRONG；挑战未过期；玩家未离开页面。
  后置条件：产生一次新的作答；答对则按 UC-R2 的成功路径结算。
  主流程：重新启用选项 → 生成新的 requestId → 按 UC-R2 提交。
  异常流程：重试时得知 41001 → 转“已过期”，提示重新遭遇。
  规则：同一道题的两次作答是两次业务操作，必须使用不同 requestId；
    只有“同一操作的网络重试”才复用原 requestId。

3.5 UC-R4 恢复结果待确认（本模块最重要的异常用况）
  参与者：玩家（主）、捕获服务（辅）
  目标：在不知道结果的情况下，查明真实状态，避免重复捕获或误报失败。
  触发：提交超时、连接中断、页面被系统回收后重新进入。
  前置条件：存在 challengeId；最近一次提交的 requestId 已知或可恢复。
  后置条件：得到三种确定结论之一——已捕获、仍可作答、已过期；或者继续停留在待确认。
  主流程：
    1) 显示“结果待确认”，禁止任何“成功”字样与本地奖励；
    2) 调用 CaptureApi.status(challengeId)；
    3) status=CAPTURED：显示成功，使用服务端返回的 captureRecordId，刷新概览；
    4) status=OPEN 且已知上次提交内容：用原 requestId 重试提交（幂等回放）；
    5) status=OPEN 且内容不可恢复：按新作答处理，生成新 requestId；
    6) status=EXPIRED：提示重新遭遇。
  异常流程：
    E1 查询本身失败：保留待确认态与原 requestId，提供手动重试，不猜测结果；
    E2 查询到 CAPTURED 但本地没有记录：仍以服务端为准，不做“本地补记”；
    E3 页面在查询完成前被关闭：下次进入以 status 查询结果为准。

3.6 UC-R5 查看收藏概览
  参与者：玩家（主）、捕获服务（辅）
  目标：看到与服务器一致的数量。
  前置条件：已登录。
  后置条件：显示 collectedSpeciesCount / totalSpeciesCount / captureCount；只读，不改变状态。
  主流程：调用 CollectionApi.summary() → 映射 CollectionSummary → 页面显示。
  异常流程：失败时显示上一次成功值并标注“未更新”，不得用本地计数冒充服务端结果。

3.7 图1 说明：答题捕获客户端用况图
  图外框是客户端系统边界，五个椭圆是玩家的五个目标，全部由玩家发起。
  UC-R1 取得题目；UC-R2 提交并查看结果；UC-R3 答错后重试；UC-R4 恢复结果待确认；
  UC-R5 查看收藏概览。虚线是依赖：UC-R3 与 UC-R4 都复用 UC-R2 的提交通道，
  区别在于前者是“新作答、新 requestId”，后者是“先查询、必要时用原 requestId 重试”。
  图下方的注说明支撑系统与红线：捕获服务提供题目与结算，SessionStore 提供身份；
  客户端不持有正确答案，也不依据本地状态发放精灵。
  图中没有把“点击选项”“点击返回”画成用况：用况表达玩家目标，不表达界面控件。

四、对象分析
====================================================================
4.1 图2 说明：客户端交互分析类图
  图按包分为四组：
  features/capture：CapturePage（界面）、CaptureController（控制）、ChallengeView（题目视图）、
    AnswerAttempt（一次作答）、CaptureResult（结算结果）；
  features/collection：CollectionPage（收藏概览界面）、CollectionSummary（概览数据）；
  data/api：CaptureApi、CollectionApi、ApiClient（统一 HTTP 与信封解析）；
  core：SessionStore（会话端口）、ApiFailure（带业务码的错误）。
  关键连线：
  CapturePage → CaptureController：用户操作只经过控制对象，页面不直接发请求；
  CaptureController → ChallengeView / AnswerAttempt / CaptureResult：控制对象持有当前题目、
    生成一次作答、产出结算结果；
  CaptureController → CaptureApi / CollectionApi：捕获与收藏分开两个接口对象，
    避免把收藏查询塞进捕获接口；
  CaptureApi → ApiClient → SessionStore：所有身份从会话端口读取，页面不接触 token；
  CaptureApi ..> ApiFailure：失败时抛出带 code 的错误，由控制对象决定提示与重试策略。
  图右侧的注写明 requestId 规则；图下方的注写明“网络未完成 ≠ 业务失败”。

4.2 类说明

  类名：CapturePage（答题界面）
  职责：呈现题目与选项，收集玩家选择，展示提交中、答错、成功、待确认、过期五种可见状态。
  属性：view｜ChallengeView｜1｜当前题目｜；submitting｜布尔｜1｜是否提交中｜。
  操作：showQuestion(ChallengeView)｜无返回｜前置：题目已取到｜后置：渲染题干与选项；
    onSubmit(optionId)｜无返回｜前置：未在提交中｜后置：转交控制对象；
    showResult(CaptureResult)｜前置：已拿到确定结果｜后置：渲染成功或答错；
    showPending()｜前置：结果不确定｜后置：显示待确认与重试入口；
    showExpired()｜前置：得知过期｜后置：提示重新遭遇。
  关联：与 CaptureController 1:1（页面生命周期内唯一）。
  主动性与多态性：被动界面对象，无子类型。
  完整性：不保存 token、不保存正确答案、不做本地发奖。

  类名：CaptureController（捕获控制）
  职责：编排一次答题的业务流程：取题、提交、超时恢复、刷新概览。
  属性：requestId｜字符串｜0..1｜当前提交的请求标识｜；current｜ChallengeView｜0..1｜当前题目｜。
  操作：loadChallenge(spawnId)｜返回 ChallengeView｜前置：有 token｜后置：保存题目；
    submit(optionId)｜返回 CaptureResult｜前置：题目有效｜后置：产生一次作答；
    recover(challengeId)｜返回 CaptureResult 或“仍未知”｜前置：发生过超时｜后置：查明状态；
    newAttempt()｜返回新 requestId｜前置：无｜后置：生成 UUID。
  关联：与 CaptureApi、CollectionApi 为依赖（调用）；与 AnswerAttempt 1:0..1（提交期间存在）。
  主动性/多态性：被动对象，由界面事件驱动；无多态需求。
  完整性：requestId 只由本人生成；不接受界面传入的 requestId，防止误复用。

  类名：ChallengeView（题目视图）
  职责：承载服务端下发的题目与展示所需字段，是界面与网络之间的只读模型。
  属性：challengeId｜字符串｜1｜；speciesName｜字符串｜1｜；questionText｜字符串｜1｜；
    options｜选项集合｜2..4｜每项 optionId + text｜；expiresAt｜时刻｜1｜UTC｜；
    sourceType｜枚举｜1｜DEV_SIMULATED / LOCATION｜。
  关联：与 CaptureController 1:1。
  完整性：字段与接口一一对应；旧字段（name/question/options[].id）不进入本对象，
    只在适配层转换一次。

  类名：AnswerAttempt（一次作答）
  职责：表达一次业务提交，是幂等判定的客户端锚点。
  属性：requestId｜字符串｜1｜一次业务操作一个｜；optionId｜字符串｜1｜来自服务端选项集合｜。
  约束：同一次提交的网络重试沿用同一 requestId；任何“重新作答”必须新生成。
  关联：与 CaptureController 0..1:1。

  类名：CaptureResult（结算结果）
  职责：表达服务端已经结算的结论，是界面显示成功的唯一依据。
  属性：result｜枚举｜1｜CORRECT / WRONG｜；captureRecordId｜字符串｜0..1｜仅 CORRECT 且已收录时非空｜；
    speciesId｜字符串｜1｜。
  约束：captureRecordId 为空时不得显示“已收入图鉴”。

  类名：CollectionPage（收藏概览界面）
  职责：展示已收录种类数、总种类数与捕获次数，并提供刷新入口。
  操作：refresh()｜前置：已登录｜后置：拉取服务器数据；showSummary(CollectionSummary)｜只读渲染。
  约束：数量来源于服务端 summary，不用本地计数 +1 代替。

  类名：CollectionSummary（收藏概览）
  属性：collectedSpeciesCount｜整数｜；totalSpeciesCount｜整数｜；captureCount｜整数｜。
  说明：totalSpeciesCount 当前实现为替身目录条目数（实测 1），接真实图鉴后为实际条目数。

  类名：CaptureApi（捕获接口）
  职责：把三个捕获动作翻译成 HTTP 调用并映射为视图模型/结果对象。
  操作：challenge(spawnId)；answer(requestId, challengeId, optionId)；status(challengeId)。
  约束：不判断业务对错，只做请求、信封解析与 DTO 映射。

  类名：CollectionApi（收藏接口）
  职责：summary() 只读查询；不与捕获接口合并。

  类名：ApiClient（统一网络层）
  职责：拼基础地址、注入身份、解析统一信封、把 HTTP 与业务错误统一成 ApiFailure。
  操作：post(path, body)；get(path)。
  约束：页面不得自己拼 URL；错误必须带 code，供上层区分过期、冲突、无权限。

  接口：SessionStore（会话端口）
  职责：提供当前 token，账号切换或 401 时清除。
  操作：token()；clear()。
  约束：网络层只依赖接口；账号页面实现该接口，二者不反向依赖。

  类名：ApiFailure（错误模型）
  属性：code｜整数｜业务码（40001/40101/40301/40401/40902/40903/41001/50301/50302）｜；
    message｜字符串｜服务端给用户看的说明｜。
  说明：网络层异常与业务失败必须分开表达；不能把“没有响应”映射成某个业务码。

4.3 关联、聚合、组合、泛化的判断
  本模块对象之间只有关联与依赖，没有聚合/组合：页面的生命周期与网络对象不同步，
  把 ApiClient 说成页面的一部分会掩盖“网络层可被多个页面共用”的事实。
  没有继承关系：不存在需要按类型分派的行为，不硬加泛化。
  依赖方向是单向的：界面 → 控制 → 网络端口；反向依赖一律禁止（见第七节）。

4.4 主动性与多态性
  全部对象为被动对象，由玩家操作与网络回调驱动。
  无多态需求：一种精灵、一道题，判题规则单一；若后续增加题型，可再引入策略对象。

4.5 完整性与访问控制
  - 身份：token 只从 SessionStore 读取，不写入日志、不放进页面状态、不出现在截图。
  - 归属：客户端不缓存他人数据；收到 40401 一律按不存在处理，不提示“这是别人的”。
  - 最小暴露：客户端不接收也不保存正确答案；题目响应中若出现答案字段，视为契约违约并按缺陷上报。
  - 账号隔离：切换账号时清空题目、结果与收藏缓存，避免两个账号串用同一份数据。
  - 成功判定：只有 result=CORRECT 且 captureRecordId 非空才算成功；HTTP 200 只说明请求被受理。

4.6 对象与用况、接口、测试的对应
  | 对象 | 主要用况 | 承载接口 | 计划测试（design/test-cases.csv） |

  | AnswerAttempt | UC-R2、UC-R3 | POST /api/v1/capture/answer | TC-R03 答对、TC-R04 答错重试 |

5.1 图3 说明：答题捕获客户端顺序图
  参与者与对象：玩家、CapturePage、CaptureController、CaptureApi、ApiClient、SessionStore、
  捕获服务。时间自上而下，先取题、再提交、再分支。
  主线：玩家点击攻城狮 → 页面请求取题 → 接口经 ApiClient 读取 token 后调用服务端 →
  返回 ChallengeView 并渲染。
  第一个 alt 是提交结果：正常返回时直接得到 CaptureResult；超时/连接中断时进入恢复分支，
  依次查询状态：CAPTURED 显示成功、OPEN 用原 requestId 重试、仍未知则停留在待确认。
  第二个 alt 是结算结果：CORRECT 刷新收藏概览；WRONG 允许重新作答。
  图中的注说明两条红线：只有 CORRECT 且 captureRecordId 非空才显示成功；
  超时先查状态，不依据本地状态自行发奖。

5.2 六类客户端场景
  S1 正常答对
    输入：有效挑战、正确选项、新 requestId。
    表现：提交中 → 成功态 → 概览刷新为服务端数量。
    结论：仅在 captureRecordId 非空时显示“已收入图鉴”。
  S2 答错后重试
    输入：先错误选项，再新 requestId 的正确选项。
    表现：第一次答错态，挑战保持可作答；第二次成功。
    结论：答错不消耗挑战；两次作答是两个业务操作，requestId 必须不同。
  S3 提交超时（本模块核心）
    输入：同一 requestId 的提交没有响应。
    表现：待确认态 → 查询状态：CAPTURED 则成功；OPEN 则用原 requestId 重试；
      查询仍失败则保持待确认并提供重试。
    结论：超时既不是成功也不是失败；客户端绝不本地发奖。
  S4 挑战过期
    输入：41001，或查询得到 EXPIRED。
    表现：过期态，提示重新遭遇。
    结论：不显示成功，不使用“网络错误”掩盖过期。
  S5 断网/服务不可达
    输入：连接失败，没有任何 HTTP 响应。
    表现：加载失败或待确认，附重试；恢复网络后可重试。
    结论：网络错误与业务错误分开表达；不把“连不上”写成“挑战过期”。
  S6 账号切换或凭证失效
    输入：40101，或玩家切换账号。
    表现：清除 token 与页面缓存，回到登录；重新进入后重新取题。
    结论：两账号缓存不串用；不清除会导致把 A 的题目提交到 B 的会话。

5.3 客户端判定次序（不得改动）
  第一步 入口校验：有 token、有 challengeId、选项来自服务端集合。
  第二步 提交：生成新 requestId，禁用重复点击与返回。
  第三步 结果判定：有响应 → 按 result 分流；无响应 → 进入恢复，不判定失败。
  第四步 恢复：查询状态优先于重试；重试优先于报错；三者都不成立才显示待确认。
  第五步 刷新：成功或返回地图后刷新概览，以服务端数量为准。
  为什么这个次序不能改：先判失败会误报，先本地加一会重复计数，先重试会在服务端已成功时
  制造一次无意义的幂等回放（本身安全，但会把“已成功”误显示为“刚提交”）。

5.4 旧 Demo 客户端与新契约的接口差异（本模块必须收敛的差异）
  现状（静态核对 main@e17aa32）：
    client/lib/features/home_shell.dart:151 调用 'capture/challenge'，请求体 {'spawnId': 'library-001'}；
    client/lib/features/capture_page.dart:45 调用 'capture/answer'，请求体只有 challengeId 与 optionId；
    client/lib/core/api.dart 使用 X-Demo-Session 头，且失败时只抛 message，不保留 code；
    server DemoController 的两个旧路由已迁移为 /api/v1/demo/capture/challenge 与
    /api/v1/demo/capture/answer（孙虹毅 foundation 交接 五、1）。
  因此现有客户端调用 /api/v1/capture/challenge 时会命中新正式接口：缺少 X-Dev-User/认证头，
  且 spawnId 'library-001' 不是 UUID，预期得到 40101 或 40001，旧演示流程会中断。
  差异与处理：
  | 项目 | 旧 Demo 客户端 | 第二阶段契约 | 客户端处理 |
  | 取题路径 | POST /capture/challenge（与新接口冲突） | POST /api/v1/capture/challenge | 统一走 CaptureApi；旧演示改用 /api/v1/demo/capture/* |
  | 作答路径 | POST /capture/answer | POST /api/v1/capture/answer | 统一走 CaptureApi，并补 requestId |
  | 身份 | X-Demo-Session | Bearer token（开发期 X-Dev-User 替身） | 由 ApiClient 统一注入 |
  | 题目字段 | name / question / options[].id | speciesName / questionText / options[].optionId | 只在适配层转换 |
  | 结果字段 | success / message | result / captureRecordId / speciesId | 只在适配层转换 |
  | 成功判定 | HTTP 200 且 code=0 | HTTP + code + result=CORRECT 且 captureRecordId 非空 | 三层都判 |
  | 错误 | message 字符串 | 业务码 40001/40101/40301/40401/40902/40903/41001/50301/50302 | ApiFailure 带 code，界面据此分流 |
  适配原则：旧字段只在 data/api 的适配器转换一次，页面与业务对象只使用新字段；
  不在页面里写 if (旧字段)。旧路由保留为独立 demo 命名空间，不与正式账号数据混用。

5.5 requestId 的三条规则
  规则1 一次业务提交一个 requestId，由 CaptureController 生成。
  规则2 同一次提交的网络重试沿用原 requestId 与原内容：服务端返回首次结果，不新增记录。
  规则3 玩家重新作答（包括答错后的重试）必须生成新 requestId；同 requestId 不同内容会得到 40902。
  反面案例：把“答错后重试”当成“重试同一次提交”去复用 requestId，会触发 40902；
  把“超时后的重试”当成新作答去生成新 requestId，会在服务端已成功时再提交一次，
  虽然唯一约束能兜住，但界面会把已成功误显示为“又提交了一次”。

6.1 图4 说明：捕获界面状态图
  本图描述 CapturePage 的界面状态，不是服务端 Challenge 的业务状态。
  七个状态：加载中 LOADING、待作答 READY、提交中 SUBMITTING、结果待确认 UNKNOWN、
  已捕获 CAPTURED、已过期 EXPIRED、加载失败 LOAD_FAILED。
  每个状态都写了入口动作：加载中入口调用 challenge；待作答入口恢复选项可点击；
  提交中入口禁用返回与重复点击；待确认入口显示“结果待确认”；已捕获入口刷新收藏概览。
  关键转换：
    待作答 → 提交中：选择选项，生成新 requestId；
    提交中 → 已捕获：CORRECT 且 captureRecordId 非空；
    提交中 → 待作答：WRONG；
    提交中 → 结果待确认：超时或连接中断；
    结果待确认 → 已捕获：查询 status=CAPTURED；
    结果待确认 → 提交中：查询 status=OPEN 且上次内容已知，用原 requestId 重试；
    结果待确认 → 待作答：查询 status=OPEN 且内容不可恢复，按新作答处理；
    结果待确认 → 已过期：查询 status=EXPIRED；
    待作答 → 已过期：收到 41001。
  图中的两条注说明：超时不等于失败也不等于成功，只有服务端结算结果才能离开待确认；
  同一 requestId 只对应一次业务提交，重新作答必须生成新标识。

6.2 状态转换明细
  | 源状态 | 事件 | 监护条件 | 动作 | 目标状态 |
  | （初始） | 进入答题页 | 有 token 与 spawnId | 调用 challenge | 加载中 |
  | 加载中 | 题目就绪 | 响应 code=0 | 保存 challengeId 与有效期 | 待作答 |
  | 加载中 | 取题失败 | 网络错误或业务错误 | 显示原因与重试入口 | 加载失败 |
  | 加载失败 | 点击重试 | 无 | 重新调用 challenge | 加载中 |
  | 待作答 | 选择选项 | 未在提交中 | 生成新 requestId、禁用控件 | 提交中 |
  | 待作答 | 收到 41001 | 无 | 提示重新遭遇 | 已过期 |
  | 待作答 | 查询发现已捕获 | 重进页面时 | 显示成功、不重复发奖 | 已捕获 |
  | 提交中 | result=CORRECT | captureRecordId 非空 | 刷新概览 | 已捕获 |
  | 提交中 | result=WRONG | 无 | 记录答错、恢复选项 | 待作答 |
  | 提交中 | 超时/连接中断 | 无 | 显示待确认 | 结果待确认 |
  | 结果待确认 | 查询 status=CAPTURED | 无 | 使用服务端记录、刷新概览 | 已捕获 |
  | 结果待确认 | 查询 status=OPEN | 已知上次内容 | 用原 requestId 重试 | 提交中 |
  | 结果待确认 | 查询 status=OPEN | 内容不可恢复 | 按新作答处理 | 待作答 |
  | 结果待确认 | 查询 status=EXPIRED | 无 | 提示重新遭遇 | 已过期 |
  | 结果待确认 | 查询失败 | 无 | 保留原 requestId | 结果待确认 |
  | 已捕获 | 返回地图 | 无 | 刷新概览 | 终态 |
  | 已过期 | 返回地图 | 无 | 提示重新遭遇 | 终态 |

6.3 为什么界面状态与服务端 Challenge 状态必须分开
  服务端 Challenge 只有 OPEN / CAPTURED / EXPIRED 三态，它描述“挑战还能不能用”。
  客户端多出的 LOADING、SUBMITTING、UNKNOWN、LOAD_FAILED 描述的是“页面现在能做什么”，
  其中 UNKNOWN 是网络状态，不是业务状态：此时服务端可能已经 CAPTURED，也可能仍是 OPEN。
  把二者混用会犯两类错误：把 UNKNOWN 当失败（误报，用户丢失已到手的收录）；
  把 UNKNOWN 当成功（重复发奖，计数与图鉴不一致）。
  因此客户端不得新增“奖励状态”，只允许新增界面状态；是否捕获以服务端为准。

6.4 可测性
  每个状态都有可断言的可见特征：加载中显示骨架、待作答显示选项、提交中选项禁用、
  待确认显示重试、已捕获显示成功文案、已过期显示重新遭遇、加载失败显示原因。
  design 阶段的 widget 测试将按状态断言，而不是只断言“页面能打开”。

八、客户端业务规则清单
====================================================================
CR-01 客户端不发放精灵：任何成功展示都必须以服务端结算结果为依据。
CR-02 成功定义：result=CORRECT 且 captureRecordId 非空，且该记录可在后续查询中读到。
CR-03 一次业务提交一个 requestId；网络重试沿用，重新作答新建。
CR-04 同 requestId 不同内容会得到 40902；客户端应把它当缺陷处理并引导重新作答。
CR-05 答错不消耗挑战：WRONG 后挑战仍可作答，界面必须允许重试。
CR-06 超时不是失败：没有响应时先查询状态，再决定重试、成功或待确认。
CR-07 41001 表示挑战或遭遇已过期：提示重新遭遇，不显示成功。
CR-08 40401 一律按“不存在”处理，不使用“无权访问”措辞，避免泄露归属。
CR-09 提交期间禁用重复点击与系统返回，防止一个动作发出多个请求。
CR-10 旧字段只在适配层转换一次，页面与业务对象只使用新字段。
CR-11 token 只从 SessionStore 读取；40101 或切换账号时清除并回登录。
CR-12 收藏数量以服务端 summary 为准，不做本地 +1。
CR-13 模拟来源必须标注：sourceType=DEV_SIMULATED 时页面写“模拟遇见攻城狮”。
CR-14 账号切换必须清空题目、结果与概览缓存，两账号数据不得串用。
CR-15 客户端不得缓存或推断正确答案；题目响应若含答案字段，按契约违约上报。

十一、本阶段结论

一次捕获在客户端“完成”的标准不是页面显示了成功，而是：
  服务端返回 CORRECT 且 captureRecordId 非空，并且在重新查询（含重启后）时仍能读到该记录。
客户端能做的是：把结果如实转述、在结果不确定时先查询、在答错时允许重试、
在任何情况下都不自行发奖、不让两个账号的数据串用。
接口差异已定位到具体文件与行：旧客户端的 capture 调用与旧路由迁移不一致，
统一网络层与新字段适配是设计阶段（10/25-10/28）的第一项工作。
